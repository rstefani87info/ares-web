# Checklist Migliorie aReS Web

- [1] 1. Correggere `jwt.js`: rimuovere l'import hard-coded da app host (`../../../app.js`), importare la libreria JWT e usare un secret derivato da `aReS.getConfig()` o `aReS.getPolicy()` con fallback legacy.
- [2] 2. Correggere `swagger.js`: eliminare variabili fuori scope (`setting`, `asyncConsole`), fix typo (`startsWith`) e rendere la generazione consistente col contratto di `XHRWrapper` del core.
- [3] 3. Rendere sicura e coerente la gestione errori in `http.js`, `server.js` e `datasources.js`: niente `stack` nei payload di risposta per default e log diagnostici solo via configurazione esplicita.
- [4] 4. Sistemare `permissions.js` affinche' il controllo consideri davvero risorsa e contesto attore, e applichi correttamente le regole di deny.
- [5] 9. Allineare il modulo web al contratto di bootstrap del core: `aReS.include(module)` richiede un oggetto con `aReSInitialize(aReS)`.
- [6] 10. Normalizzare l'identita' di sessione sulle request (`req.sessionId`) in modo coerente tra web e core, evitando dipendenze da dettagli di `express-session` (`req.session.id`).
- [7] 11. Rendere `cors()` configurabile con default conservativi o documentati chiaramente, senza assumere che un framework debba aprire tutto per ogni applicazione.
- [8] 12. Esporre opzioni robuste per `express-session`, inclusi `secure`, `httpOnly`, `sameSite` e store esterni, evitando di imporre scelte insicure ai consumer.
- [9] 13. Consentire di configurare `express.json()` con limiti e parser custom, per non vincolare tutte le applicazioni allo stesso comportamento.
- [10] 14. Chiarire come vengono registrate le datasource REST e se l'auto-export debba essere opt-in invece che implicito.
- [11] 1. Correggere i bug runtime in `jwt.js` e rimuovere le dipendenze implicite da struttura applicativa esterna.
- [12] 2. Correggere i bug bloccanti in `swagger.js` per rendere il modulo almeno eseguibile e verificabile.
- [13] 3. Correggere `permissions.js` per applicare regole coerenti su risorsa, actor context e deny-list.
- [14] 4. Rendere `sendError()` e il logging di `server.js` sicuri per una libreria, con diagnostica opzionale e non invasiva.
- [15] 5. Sistemare `isProduction()` e `normalizeMethodsArray()` per eliminare errori logici di base.
- [16] 10. Esporre configurazione esplicita per `cors()`, `express.json()` e `express-session`.
- [17] 11. Definire default conservativi e override semplici per i consumer del framework.
- [18] 12. Chiarire se l'auto-export delle datasource REST debba essere opt-in o configurabile per ambiente.
- [19] 13. Distinguere opzioni obbligatorie, opzionali e fallback in `appSetup`.
- [20] 22. Verificare la stabilita' e la dimensione di header custom come `X-aReS-Metadata`.
- [21] 23. Valutare la scomposizione di moduli accessori per ridurre il peso del pacchetto base.
- [22] 24. Introdurre esempi applicativi separati dalla libreria per evitare coupling tra framework e app host.
- [23] 25. Valutare una policy di versioning semantico esplicita per le API pubbliche del modulo `web`.
