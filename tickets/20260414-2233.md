# Checklist Migliorie aReS Web

## Alta Priorita
- [x] Correggere `jwt.js`: rimuovere l'import hard-coded da app host (`../../../app.js`), importare la libreria JWT e usare un secret derivato da `aReS.getConfig()` o `aReS.getPolicy()` con fallback legacy.

> Nota: oggi `jwt.js` usa `jwt.verify()` e `jwt.sign()` senza import, usa `sessionId` non definita (`req.session[sessionId]`) e dipende da `appSetup.jwtSecret` letto da un file esterno al package. Inoltre l'ID sessione va normalizzato (preferire `req.sessionId` / `req.sessionID`) invece di leggere `req.session.id`.

- [x] Correggere `swagger.js`: eliminare variabili fuori scope (`setting`, `asyncConsole`), fix typo (`startsWith`) e rendere la generazione consistente col contratto di `XHRWrapper` del core.

> Nota: oggi `exportDatasourceQueryAsSwaggerSetupService()` usa `setting` e `asyncConsole` senza scope/import, `startWith()` non esiste, e `generate()` usa `XHRWrapper.post()` senza `await` e poi legge `response.data` invece di `response.results` (shape del core: `{ status, message, results, €rror }`).

- [x] Rendere sicura e coerente la gestione errori in `http.js`, `server.js` e `datasources.js`: niente `stack` nei payload di risposta per default e log diagnostici solo via configurazione esplicita.

> Nota: `http.sendError()` include `error.stack` nel JSON per default e contiene un bug di closure (usa `error` invece del parametro `e` del formatter). In `server.js` ci sono log operativi su `console.log` condizionati in modo invertito (stampa quando `aReS.isProduction` e' true). In `datasources.js` vengono usati 403 anche per errori interni (catch generico) e si serializza metadata in header senza limiti.

- [x] Sistemare `permissions.js` affinche' il controllo consideri davvero risorsa e contesto attore, e applichi correttamente le regole di deny.

> Nota: oggi `getPermission()` ha condizioni sempre-true (`.length >= 0`), una deny-list che consulta il campo sbagliato (`dontAllowOnlyForUserId` confrontato su `allowOnlyForUserId`) e un modello sessione fragile (`req.session.id` invece di `req.sessionId`/`req.sessionID`). Inoltre `permissionFail()` assume `req.res` e non riceve `res` come parametro.

## Contratto Framework
- [x] Definire API pubbliche chiare per `aReSInitialize`, `exportRESTRoute`, `validateJWT`, `getRoutes` e `isResourceAllowed`, distinguendo cosa e' supportato da cio' che e' solo dettaglio interno.
- [x] Evitare dipendenze da struttura applicativa esterna, come l'import diretto di `../../../app.js` in `jwt.js`; una libreria framework dovrebbe ricevere secret e strategy via configurazione o dependency injection.
- [x] Rivedere gli accessi a campi interni di Express come `aReS.httpServer._router.stack`, perche' non sono un contratto stabile e possono rompersi con upgrade futuri.
- [x] Evitare override invasivi di `res.send`, `res.json` e `res.setHeader` come default di libreria; se servono, esporli come hook o middleware opzionale.

## Integrazione con @ares/core (post-fix core)
- [x] Allineare il modulo web al contratto di bootstrap del core: `aReS.include(module)` richiede un oggetto con `aReSInitialize(aReS)`.

> Nota: il core espone `include()` e i nuovi accessor `getConfig()`/`getPolicy()`. Il web deve consumare quel contratto (es. permessi da `aReS.getPolicy('permissions')`, JWT secret da `aReS.getConfig('jwt.secret')` o chiavi equivalenti) mantenendo fallback alle chiavi legacy in `appSetup`.

- [x] Normalizzare l'identita' di sessione sulle request (`req.sessionId`) in modo coerente tra web e core, evitando dipendenze da dettagli di `express-session` (`req.session.id`).

> Nota: nel core `datasources.js` e' stato reso robusto anche senza `req.session.id`. Il web deve passare un contesto minimo consistente e non assumere che `req.session` contenga un campo `id`.

## Configurabilita e Default
- [x] Rendere `cors()` configurabile con default conservativi o documentati chiaramente, senza assumere che un framework debba aprire tutto per ogni applicazione.
- [x] Esporre opzioni robuste per `express-session`, inclusi `secure`, `httpOnly`, `sameSite` e store esterni, evitando di imporre scelte insicure ai consumer.
- [x] Consentire di configurare `express.json()` con limiti e parser custom, per non vincolare tutte le applicazioni allo stesso comportamento.
- [x] Chiarire come vengono registrate le datasource REST e se l'auto-export debba essere opt-in invece che implicito.

## Packaging
- [x] Allineare `package.json` all'uso reale della libreria: l'entrypoint dichiarato deve esistere e rappresentare la superficie pubblica del pacchetto.
- [x] Dichiarare in `dependencies` o `peerDependencies` tutti i moduli realmente necessari a runtime, distinguendo quelli opzionali o usati solo da feature secondarie.
- [x] Valutare se moduli come Swagger code generation, `whois` o utilita' non core debbano stare in entrypoint separati, per non appesantire il pacchetto base.
- [x] Verificare gli import tra pacchetti monorepo, come `@ares/web/http.js`, per assicurare che funzionino sia in workspace sia dopo publish.

## Robustezza
- [x] Correggere `isProduction()` in `server.js`, che oggi ha una logica fragile e puo' restituire risultati errati.
- [x] Correggere `normalizeMethodsArray()` in `http.js`, eliminando i riferimenti errati a `int` e la gestione non affidabile dei numeri.
- [x] Rivedere `getPermission()` per usare condizioni booleane corrette, regex sicure e naming coerente tra allow-list e deny-list.
- [x] Verificare che gli header custom come `X-aReS-Metadata` non eccedano dimensioni ragionevoli e che il payload resti stabile per i consumer.

## Qualita e Adozione
- [x] Aggiungere test di smoke per bootstrap server, protezione JWT, permessi e registrazione route, cosi' da proteggere il contratto del framework.
- [x] Aggiungere test mirati per il modulo Swagger, almeno sulla generazione minima dello schema e sugli errori piu' evidenti.
- [x] Migliorare `README.md` con esempi di integrazione, configurazione minima e distinzione tra API stabili e funzionalita' avanzate.
- [x] Documentare quali opzioni sono obbligatorie in `appSetup` e quali hanno fallback sensati, per ridurre integrazioni fragili nei progetti che usano il framework.
